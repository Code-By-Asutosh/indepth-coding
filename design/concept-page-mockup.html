Two Pointers // every comparison deletes a whole row of possibilities

corefreq: highpattern~6 min+120 xp
Picking up where we left off

ShopSphere's Diwali sale went live at midnight. By 12:04, support tickets started arriving: "I used my ₹500 gift card on a ₹480 order and the app just spins." Somewhere in checkout, code was hunting for two priced items that exactly exhaust a gift card — and doing it so slowly that requests were timing out. This lesson is the fifteen minutes that fix it forever.

01 The gift-card bug

Here's the code Riya wrote first — and honestly, it's the code almost everyone writes first. Check every pair. If any pair hits the gift-card amount exactly, win:

CheckoutService.java — v1, the version that timed out
// for n products → n × n comparisons. At 100k products, ten billion.
for (int i = 0; i < prices.length; i++) {
  for (int j = i + 1; j < prices.length; j++) {
    if (prices[i] + prices[j] == giftCard) return true;
  }
}
return false;

It's correct. It also compared the same pairs over and over, learning nothing from each answer. Every "no" told us nothing about which pairs we could skip next. That's the whole disease.

But ShopSphere's catalog has one quiet superpower we weren't using: prices are already sorted — the search results page demands it. Sorted means the cheapest item sits at one end and the priciest at the other. And that arrangement has a property we're about to exploit brutally.

Cheapest + most expensive is the only pair where ONE comparison tells you which item is innocent — always.

02 Walking from both ends

Put one finger on the cheapest product, one on the costliest, and ask a single question: sum ?= 500.

If the sum is too big, there is exactly one guilty party: the expensive item. It's already paired with the smallest possible partner and still overshot — so nothing cheaper-in-the-middle can save it. Retire it, move the right finger in. If the sum is too small, symmetric logic retires the cheap item instead. Either way, one comparison permanently eliminates one full row of possibilities. No second chances, no re-checking — each item leaves the dance floor exactly once.

Two fingers, walking inward. That's the entire algorithm. Don't take the walk on faith though —

    03 The Java, explained by what you just watched

    Every frame you just scrubbed through maps to exactly one line below. Nothing more happens in the code than happened on the shelf:

    CheckoutService.java — v2, shipping tonight
    boolean pairExists(int[] prices, int giftCard) {
  int left = 0, right = prices.length - 1;   // fingers on the extremes
  while (left < right) {                      // crossed ⇒ every pair was judged
    int sum = prices[left] + prices[right];
    if (sum == giftCard) return true;       // 🎯 gift card exhausted exactly
    if (sum > giftCard) right--;              // too rich ⇒ retire the expensive item
    else left++;                               // too poor ⇒ retire the cheap one
  }
  return false;                                // walked clean through: provably no pair
}

    Notice what disappeared: the inner loop. Ten billion comparisons became at most n − 1. At ShopSphere's Black-Friday scale, that's the difference between a 4-second request and a sub-millisecond one.

    04 Honest costs

    This trick has an entry fee people discover in interviews the hard way: it only works on sorted data. ShopSphere gets sorting for free because the catalog lives sorted anyway. If your data isn't sorted, you pay O(n log n) to sort first — still cheaper than the brute-force O(n²), but suddenly not free.

    And when the array is unsortable — streaming items, or you need the actual indices of unsorted input — a HashSet beats it outright: one pass, have I seen 27 − x?, done in O(n) with no ordering required. Two Pointers wins when the data is sorted or becomes sorted cheaply; the HashSet wins when it doesn't. Neither is "the best one." Senior engineers carry both.

    ShopSphere checkout — put together
    • Brute force checked every pair and learned nothing from each failure → O(n²), timed out.
    • Sortedness was the unused superpower already sitting in the catalog.
    • Opposite-ends walk: too big kills the right item, too small kills the left — one comparison, one elimination.
    • Crossing pointers are mathematical proof that no pair exists. 7 comparisons replaced 21.
    • Gift-card checkout now answers in microseconds. Ticket closed. 🎉

    ⚔ war room // interview-prep appendix — after the story, before the room
    RF·1 What is the two-pointer technique in one breath? ▸
    Walk two indices through a sorted collection from opposite ends (or the same direction), using one comparison per step to permanently discard a whole class of candidates — turning O(n²) pair-scanning into O(n).
    RF·2 Why does moving the right pointer on "too big" never skip the answer? ▸
    Because it's paired with the smallest remaining value and still overshoots. Every other candidate partner is larger, so every pair containing the right item also overshoots. Discarding it loses nothing — that's the invariant.
    RF·3 Loop condition: left < right or left ≤ right? ▸
    For pair-sum: <. A pair needs two distinct elements; letting them meet would test an element paired with itself. (For "square of a sorted array"-style problems where one element can fill both slots, ≤ appears — know which contract you're in.)
    DRILL Interviewer: "Your pair-sum API serves unsorted price feeds from vendors. Does two-pointers die?" ▸
    State the trade first: sorting costs O(n log n) once if the feed is static, so sort-and-walk still beats O(n²). But if the feed is a hot stream with frequent inserts, maintain a HashSet of complements instead — O(n) time, O(n) space, zero ordering assumption. Name the invariant you'd be giving up (sortedness) and what replaces it (complement membership). That escalation-path shape is the senior signal.
